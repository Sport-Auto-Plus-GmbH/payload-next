# Naming Conventions

This document defines the **required** naming conventions for this project, from the first
collection onward. They intentionally differ by layer — do not flatten everything to one
casing style, and do not introduce a second convention "temporarily."

---

# Language

All identifiers MUST be written in English. Admin-facing `label`s and content strings are
German (the CMS's primary editorial language) — that is content/labels, not identifiers, and
may stay German. Never mix languages within an identifier itself.

---

# Collections and Globals

The folder and the main file share one **PascalCase** name matching the exported config:

```
collections/BlogPosts/BlogPosts.ts   → export const BlogPosts: CollectionConfig
globals/Header/Header.ts             → export const Header: GlobalConfig
```

## Slugs

`slug` (and any collection reference by slug, e.g. in `relationTo`, a plugin's collection
map, or `seoPlugin({ collections: [...] })`) MUST be **kebab-case**, plural for collections,
singular for globals:

```
slug: 'blog-posts'
slug: 'faq-categories'
slug: 'header'        // global
```

Once a collection ships (i.e. a migration exists and any environment has real data), its
`slug` is a breaking-change surface — see `backend/REST_API.md`.

## `dbName`

Set a short `dbName` on a collection proactively when its slug or generated block/relation
table names are likely to exceed Postgres's identifier length limits (deeply nested blocks,
long relationship table names) — decide this when the collection is first created, not as a
later fix. Once set and migrated, `dbName` MUST NOT change without a deliberate rename
migration.

---

# Hooks, Access, Utilities, Blocks, Constants, Seeds

Everything under `hooks/`, `access/`, `utilities/`, `constants/`, `seeds/`, `blocks/layouts/`,
and block folder names under `blocks/content/` uses **camelCase** file names, exporting a
camelCase function/constant of the same name:

```
hooks/formatSlug.ts             → export const formatSlug = (...)
hooks/ensureUniqueSlug.ts
access/isSuperAdmin.ts          → export const isSuperAdmin = (...)
utilities/getUserTenantIDs.ts   → export const getUserTenantIDs = (...)
blocks/content/blogListing/     block folder name matches its blockType/slug in camelCase
```

Access functions MUST use this fixed naming set for every collection, so imports read the
same way everywhere: `createAccess`, `readAccess`, `updateAccess`, `deleteAccess` (imported
as `import { createAccess, readAccess, updateAccess, deleteAccess } from
'@/collections/shared/access'` whenever the shared defaults apply).

---

# Admin Components

Custom Payload admin field/UI components under `components/` use **PascalCase** `.tsx` file
names matching the exported component:

```
components/ColorPickerField.tsx    → export function ColorPickerField(...)
components/IconSelectField.tsx
```

A small camelCase helper file colocated with one or two components (shared defaults, shared
option lists) is acceptable here — see `core/FOLDER_STRUCTURE.md`.

---

# Migrations

Migration file names are generated by Payload's CLI (`pnpm migrate:create <name>`) as
`YYYYMMDD_HHMMSS_<name>.ts` or `YYYYMMDD_HHMMSS.ts`. Always use the CLI so the timestamp
prefix and internal migration name stay consistent with `migrations/index.ts` — never
hand-name a migration file.

---

# Fields

Field `name` values (the actual database column / API key) are **camelCase**:

```ts
{ name: 'featuredImage', type: 'upload', ... }
{ name: 'showAdditionalTopicLabels', type: 'checkbox', ... }
```

Field `label`s are the human-readable German editorial label, independent of the field name.

---

# TypeScript Types

Generated types live only in `payload-types.ts` (never hand-edit; regenerate with
`pnpm generate:types`). Hand-written helper types colocated with a hook/utility should use
PascalCase type names describing the concept (`ResolvedTenantSlug`, not `Type1`).

---

# Booleans

Boolean field names and variables should answer a question: `allowPublicRead`,
`showAdditionalTopicLabels`, `indexPage`. Avoid bare nouns like `public`, `visible`.

---

# Review Document Names

Review artifacts under `reviews/` are an exception to the layer-based rules above because
they MUST be chronologically sortable:

```
reviews/<branch-folder>/YYYY-MM-DD_HH-MM-<slug>.md
```

`<branch-folder>` is the branch name with `/` replaced by `-`.

---

# Naming Checklist

Before introducing a new name ask:

- Does it follow this layer's required casing (PascalCase config, camelCase logic,
  kebab-case slug)?
- Is it written in English?
- Does it match the naming already established by the first collections/hooks/utilities
  built in this project?
- Would another engineer immediately know where to find it from its name alone?
